# AWS deployment guide

CostGuard runs on AWS in one region per installation: a US region for US customers, an EU region for EU customers
([ADR 0078](adr/0078-aws-us-eu.md)). `deploy/terraform/aws` creates the infrastructure; the Helm chart
`deploy/helm/costguard` deploys the application into it.

> Status: the Terraform module passes `terraform fmt -check`, `terraform validate` and a static security scan
> (checkov, results below). It has **not** been applied to an AWS account: no account or credentials were available.
> `terraform plan` against a real account is the first step of the first deployment. Nothing in this repository
> creates resources by itself.

## Architecture

```
                     Route 53 / your DNS
                            │
                  AWS Load Balancer (ingress-nginx, TLS, rate limits)
                            │
 ┌──────────── VPC (2–3 AZs) ─────────────────────────────────────────────────────────┐
 │ public subnets: NAT gateway(s), load balancer                                      │
 │ private subnets:                                                                    │
 │   EKS managed nodes (IMDSv2, encrypted disks)                                       │
 │     web client · core · gateway · ingest · reports · anomaly · Keycloak (chart)     │
 │     Schema Registry · ClickHouse (self-run) or ClickHouse Cloud via PrivateLink     │
 │   RDS PostgreSQL 17 (Multi-AZ in prod) · ElastiCache Redis 7.1 (TLS + AUTH)         │
 │   MSK Kafka (SASL/SCRAM over TLS)                                                   │
 │ S3 gateway endpoint → buckets: imports, backups, mlflow, logs (SSE-KMS, TLS only)  │
 └─────────────────────────────────────────────────────────────────────────────────────┘
 ECR repositories (scan on push, immutable tags) · one KMS key (rotation on) · Secrets Manager
 CloudWatch: EKS control plane (api, audit, authenticator), MSK brokers, rejected VPC flows
```

| Concern | How |
|---|---|
| Network | Private subnets for everything with data; security groups admit PostgreSQL, Redis and Kafka only from the EKS cluster; the VPC default security group allows nothing; rejected flows logged |
| Kubernetes API | Private endpoint; a public one only for the CIDRs in `cluster_admin_cidrs` |
| Identity | Pods get S3 access through an IAM role of their service account (IRSA): no static S3 keys |
| Secrets | Generated by Terraform into Secrets Manager (KMS-encrypted); RDS manages its own master password; nothing secret in outputs |
| Encryption at rest | KMS for EKS secrets, RDS, ElastiCache, MSK, S3, ECR, EBS, CloudWatch Logs, Secrets Manager |
| Encryption in transit | `rds.force_ssl=1`, Redis TLS, Kafka TLS (client and in-cluster), S3 TLS-only bucket policy, TLS at the ingress |
| Backups | RDS automated backups (`backup_retention_days`, 30 in the prod examples), final snapshot in prod, deletion protection in prod; the chart's backup CronJob writes dumps to the versioned backups bucket |
| Monitoring | CloudWatch logs above; Prometheus and Grafana from the chart (`monitoring`), RDS Performance Insights |
| Tags | `Project`, `Environment`, `DataRegion`, `ManagedBy` on every resource, plus `tags` |

## US and EU

| | US | EU |
|---|---|---|
| Example | `us-prod.tfvars.example` (`us-east-1`) | `eu-prod.tfvars.example` (`eu-central-1`) |
| Allowed regions | `us-east-1`, `us-east-2`, `us-west-2` | `eu-central-1`, `eu-west-1`, `eu-north-1` |
| State | its own state file (`aws/prod/us-east-1/...`) | its own state file (`aws/prod/eu-central-1/...`) |
| Keycloak | in the same region (chart `keycloak.enabled`) | in the same region |
| Stripe | one Stripe account can serve both; webhooks go to each installation's own endpoint | |

The two installations share nothing: separate VPCs, databases, buckets, keys. Personal data of EU customers stays in
the EU installation (see `docs/legal/` for the subprocessor list and transfer notes). The Helm value `region` must
equal the Terraform `region`; the chart knows the S3 endpoint of each allowed region.

## Prerequisites

1. An AWS account of the operating company (not a Russian legal entity: AWS and Stripe will not serve one), with
   billing alerts set.
2. An IAM principal for Terraform with administrator rights in that account (narrow it after the first apply).
3. Terraform ≥ 1.6 (CI uses 1.9.8), `kubectl`, `helm` 3, AWS CLI v2.
4. A state bucket and lock table (`backend.tf.example`).
5. A domain for the web client, the API, the gateway and Keycloak, and certificates (cert-manager with Let's
   Encrypt in the cluster, as the chart expects, or ACM on the load balancer).
6. ClickHouse: ClickHouse Cloud in the same region (reached privately), or ClickHouse run in the cluster with the
   Altinity operator. Terraform does not create it.
7. A Confluent-compatible Schema Registry in the cluster (the `cp-schema-registry` image under the Confluent
   Community License, or Apicurio Registry in its Confluent-compatible mode); MSK has none. Point it at MSK with the
   same SCRAM user.

## Cost considerations (estimates, not quotes)

On-demand list prices in `us-east-1` at the time of writing, before taxes, data transfer and support; check the AWS
Pricing Calculator before committing. EU regions are typically 5–15% more.

| Item | Staging defaults | Prod example |
|---|---|---|
| EKS control plane | ~$73/mo | ~$73/mo |
| Nodes | 2 × t3.xlarge ≈ $240/mo | 3 × m6i.xlarge ≈ $420/mo |
| NAT gateway(s) | 1 ≈ $33/mo + traffic | 3 ≈ $100/mo + traffic |
| RDS PostgreSQL | db.t4g.medium single-AZ ≈ $55/mo + storage | db.m7g.large Multi-AZ ≈ $300/mo + storage |
| ElastiCache Redis | 1 × cache.t4g.small ≈ $25/mo | 2 × cache.m7g.large ≈ $230/mo |
| MSK | 2 × kafka.t3.small ≈ $65/mo + storage | 3 × kafka.m7g.large ≈ $460/mo + storage |
| S3, ECR, KMS, CloudWatch, Secrets Manager | tens of dollars | tens to low hundreds |
| **Rough total** | **~$550–650/mo** | **~$1,700–2,000/mo** + ClickHouse |

Cheaper staging: fewer/smaller nodes, `t3.large`, stop the node group out of hours. MSK is the largest fixed cost;
for a single small customer a self-run Kafka in the cluster is an option (not provided here).

## Plan first, without applying

`terraform plan` creates nothing and costs nothing. It needs only the account id and the availability zones, so the
identity that runs it can have the two permissions of [`deploy/terraform/aws/plan-policy.json`](../deploy/terraform/aws/plan-policy.json).

1. **The account** (the owner, by hand): sign up at aws.amazon.com with the operating company's details and card, turn
   on MFA for the root user, set a billing alarm. Nobody else should hold the root credentials.
2. **A plan-only identity:** IAM → Users → `costguard-plan`, no console access; attach an inline policy with the
   content of `plan-policy.json`; create an access key ("Command Line Interface").
3. **The profile, in your own terminal** (never paste keys into a chat or a file in the repository):
   `aws configure --profile costguard-plan` (region `us-east-2`), or write `~/.aws/credentials` by hand:
   ```ini
   [costguard-plan]
   aws_access_key_id = AKIA...
   aws_secret_access_key = ...
   ```
4. **Run:** `AWS_PROFILE=costguard-plan tools/terraform/plan_staging.sh` — plan without a state backend, then
   `tools/terraform/check_plan.py` (only creations; US/EU region; tags; no public database, cache, bucket or API;
   encryption; no security group open to the internet) and checkov on the plan if installed.
5. Delete or deactivate the access key when the plan is reviewed; `terraform apply` needs a different, broader
   identity and a decision to pay.

Rehearsed on 2026-11-24 against a local AWS API stand-in (moto 5.2, AWS provider 5.x, Terraform 1.9.8; no AWS
account): staging **112 to add, 0 to change, 0 to destroy**; `us-prod` and `eu-prod` examples **121 to add** each;
`check_plan.py` passed on all three; with `cluster_admin_cidrs=["0.0.0.0/0"]` it fails, and `region=ap-south-1` is
refused by the module. checkov on the staging plan: 231 passed, 35 failed — the kinds already accepted in the
static scan (counted per bucket a little differently on a plan) plus four that follow from the cheap staging
defaults and are absent from both prod plans: RDS and ElastiCache without Multi-AZ (CKV_AWS_157, CKV2_AWS_50), RDS
without deletion protection (CKV_AWS_293), and the EKS API reachable from `cluster_admin_cidrs` (CKV_AWS_39). The plan against a
real account is still to be run.

## Deployment

1. **State.** Copy `backend.tf.example` to `backend.tf`, fill in the bucket, key and region.
2. **Variables.** Copy the example for your environment to `prod.tfvars` (not committed) and review it.
3. **Plan and apply.**
   ```bash
   cd deploy/terraform/aws
   terraform init
   terraform plan -var-file=prod.tfvars -out=plan.out
   terraform apply plan.out            # about 30–40 minutes: EKS and MSK take the longest
   aws eks update-kubeconfig --region <region> --name costguard-prod
   ```
4. **Database roles.** The application must connect as an ordinary role, never as the master user: row-level
   security does not apply to owners of tables that bypass it, and the isolation of companies depends on it. With the
   master password from `postgres_master_secret_arn`, from a pod in the cluster:
   ```sql
   CREATE ROLE costguard LOGIN PASSWORD '<generate>' NOSUPERUSER NOBYPASSRLS;
   GRANT ALL ON DATABASE costguard TO costguard;
   ALTER DATABASE costguard OWNER TO costguard;
   ```
   Flyway (in the core) then creates the tables as `costguard`. Create `costguard_backup` as in
   `tools/backup/grant-backup-role.sql`.
5. **Kubernetes secret** `costguard-secrets` (docs/runbooks/secrets.md) with, among others:
   `DB_USER=costguard`, `DB_PASSWORD`, `REDIS_PASSWORD` (from `redis_secret_arn`), `SPRING_DATA_REDIS_SSL_ENABLED=true`,
   the Kafka client settings for SASL/SCRAM over TLS:
   `SPRING_KAFKA_SECURITY_PROTOCOL=SASL_SSL`, `SPRING_KAFKA_PROPERTIES_SASL_MECHANISM=SCRAM-SHA-512`,
   `SPRING_KAFKA_PROPERTIES_SASL_JAAS_CONFIG=org.apache.kafka.common.security.scram.ScramLoginModule required username="costguard" password="<from kafka_secret_arn>";`
   (and the same for the Python services and KEDA, `keda.kafkaAuth`), the ClickHouse credentials, the receipt signing
   key, `CONNECTIONS_ENCRYPTION_KEY`, the Keycloak client secrets and, for billing, the Stripe settings
   ([STRIPE_SETUP.md](STRIPE_SETUP.md)). Do **not** set `S3_ACCESS_KEY`/`S3_SECRET_KEY`: the pods use the IAM role.
   Prefer the External Secrets Operator reading Secrets Manager over copying values by hand.
6. **Images.** Push the CI images to the ECR repositories (`registry` output), tag = commit.
7. **Helm values** (`values-aws-prod.yaml`, not committed):
   ```yaml
   image: { registry: <registry output>, tag: <commit> }
   region: us-east-1
   serviceAccount:
     create: true
     name: costguard
     annotations: { eks.amazonaws.com/role-arn: <workloads_role_arn output> }
   external:
     kafkaBootstrapServers: <kafka_bootstrap_servers>
     schemaRegistryUrl: http://schema-registry:8081
     postgresUrl: <postgres_url>
     redisHost: <redis_host>
     clickhouseUrl: https://<your ClickHouse>:8443
   imports: { bucket: <imports_bucket> }
   ingress: { enabled: true, hosts: { web: app.example.com, api: api.example.com, gateway: gateway.example.com, keycloak: id.example.com } }
   keycloak: { enabled: true }
   ```
   then `helm upgrade --install costguard deploy/helm/costguard -n costguard --create-namespace -f values-aws-prod.yaml`.
8. **Topics and ClickHouse tables**: the chart's jobs create them (`clickhouseMigrations`, topic job).
9. **Smoke test**: `tests/smoke/test_staging.py` against the new hosts.

## Rollback

- **Application:** `helm rollback costguard <revision>`. Flyway migrations only add; a release whose migration ran
  cannot be rolled back below it without restoring the database, so test migrations on staging first.
- **Infrastructure:** revert the Terraform change and apply again. Changes that replace RDS, MSK or ElastiCache
  (shown as `must be replaced` in the plan) lose data: never apply such a plan to prod without a fresh snapshot.
- **Database:** restore an RDS snapshot or a point in time into a new instance, point `external.postgresUrl` at it.
- **Destroy:** prod has deletion protection on RDS and buckets that refuse deletion with data; staging is removable
  with `terraform destroy`.
