# 0019. Подключённые системы: список в ядре, команды и отчёты агента через Kafka

## Контекст
Странице «Подключённые системы» нужны список систем компании (тип, статус, последняя синхронизация, число
загруженных записей, последняя ошибка) и действия «подключить», «отключить», «синхронизировать сейчас». На доске
коннекторы есть, но страницы и обратной связи от них нет. Раньше агент коннекторов знал о системах только из своего
TOML-файла, а ядро ничего не знало о том, как прошла выгрузка. Агент работает либо в Airflow (`--once` раз в час,
DAG `connectors_hourly`), либо постоянно в сети клиента, и в обоих случаях у него уже есть Kafka.

## Решение
- Список систем ведёт ядро, модуль `connections` (таблицы `connection`, `connection_run`, RLS по tenant).
  Одна система каждого типа на компанию: курсор агента хранится по типу. В ядре лежат только настройки, которые
  не секреты; допустимые ключи для каждого типа перечислены в `SystemTypes`, любой другой ключ отклоняется
  (`setting_unknown`), поэтому пароль или токен в ядро не попадёт. Секреты остаются в окружении агента или в Vault;
  `GET /api/v1/connections/types` называет переменные, которые агенту нужны.
- `connectors.config.v1` (compacted, ключ `tenant_id:type`): ядро публирует полное состояние подключения через
  outbox при подключении, отключении и запросе синхронизации. Агент читает топик целиком при каждом цикле и
  накладывает его на свой файл: подключённая система добавляет или заменяет секцию, отключённая не выгружается,
  даже если есть в файле. `from_core = false` в файле оставляет агента только на файле. Если топик недоступен,
  агент работает по файлу.
- «Синхронизировать сейчас» — команда в том же топике (`sync_requested_at`). Постоянно работающий агент раз в
  минуту проверяет, не запрошена ли синхронизация после его последнего запуска системы, и выгружает её сразу.
  Агент в Airflow выполнит её в следующий часовой запуск; API отвечает 202 и статусом `sync_requested`.
- `connectors.runs.v1` (ключ `tenant_id:type`): агент сообщает о каждой выгрузке — время, успех или ошибка,
  число опубликованных сущностей и записей затрат. Из ошибки вырезаются значения секретов окружения.
  Ядро читает топик в `shared/inbox` (группа `core-connections`), повтор отчёта не учитывается дважды. Система,
  настроенная только в файле агента, появляется на странице после первого отчёта (`managedInCore = false`);
  подключение её из ядра забирает управление настройками.
- Статус выводится из последних запусков: `pending` (ещё не выгружалась), `connected`, `failing`,
  `sync_requested`, `disconnected`. Отключение не удаляет историю.
- Менять подключения могут роли `owner` и `it_admin` (`@ManagesConnections`); смотреть — любой пользователь компании.

## Последствия
- Два новых топика, которых нет на доске (`schemas/avro/README.md`); контрактные тесты покрывают оба направления.
- Секреты по-прежнему настраиваются вне продукта: подключить систему на странице мало, нужны переменные в окружении
  агента. Пока их нет, запуск приходит с ошибкой `Missing setting or secret ...`, и это видно на странице.
- Агент в Airflow не реагирует на «синхронизировать сейчас» мгновенно. Если понадобится, DAG можно запускать
  по событию из топика (сенсор Kafka), это отдельное решение.
- Каждый цикл агент перечитывает compacted-топик целиком; при тысячах компаний в одном топике стоит перейти на
  долгоживущего потребителя с фильтром по tenant.

## Дополнение: ручной запуск через Airflow
Агент в Airflow раньше выполнял «синхронизировать сейчас» только в следующий часовой запуск. Теперь, если задан
`AIRFLOW_URL`, ядро после запроса синхронизации запускает DAG `costguard_connector_sync` через REST API Airflow 2
(`dag_run_id = manual-<connection_id>-<время запроса>`, повтор даёт 409 и второго запуска нет). DAG выполняет
`costguard-connector-agent <tenant>.toml --once --only <type>`; агент, как всегда, берёт подключение из
`connectors.config.v1` и сообщает о выгрузке в `connectors.runs.v1`. Если Airflow не ответил, API всё равно отвечает
202: запрос остаётся в топике, и агент выполнит его в следующий запуск. Без `AIRFLOW_URL` всё работает как раньше.
У Airflow должен быть включён basic auth для REST API (`AIRFLOW__API__AUTH_BACKENDS`, в локальном compose задан).
