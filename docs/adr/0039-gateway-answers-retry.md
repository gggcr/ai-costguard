# 0039. Шлюз отвечает на повтор операции её первым ответом

Статус: принято, 2026-11-10.

## Контекст

На кадре 3 доски третья ступень шлюза при повторе операции отвечает «из кэша или 409 duplicate_operation». В коде
был только 409. Агент, у которого оборвалось соединение или истёк таймаут, повторяет запрос с тем же
`Idempotency-Key`. Он получал 409 и не знал, прошла операция или нет. Деньги при этом уже были списаны, а ответ
модели или платного API потерян.

## Решение

- `answers/AnswerCache`: ответ операции, которая прошла, хранится в Redis рядом с её резервом
  (`cg:{tenant}:c:<operation>`). Хранятся статус, тип содержимого и тело. Срок хранения —
  `costguard.gateway.answer-ttl` (24 часа), предел размера — `costguard.gateway.answer-max-bytes` (1 МиБ).
- Сохраняются только ответы, после которых операция рассчитана: прокси модели или платного API с ответом без
  ошибки (поток сохраняется целиком и отдаётся одним куском) и `POST /v1/spend/authorize`, который прошёл лестницу.
- Третья ступень (`LoopFilter`) при повторе ищет сохранённый ответ. Если он есть, лестница возвращает
  `StepResult.Answered`, и агент получает тот же ответ с заголовком `X-CostGuard-Replayed: true`. Операцию больше не
  проверяют, не резервируют, не списывают и не записывают в журнал второй раз.
- Ответа нет, если первая попытка ещё идёт, ответ слишком велик или срок хранения истёк. Тогда остаётся
  `409 duplicate_operation`, как раньше.
- Ответ с ошибкой провайдера не сохраняется: резерв уже возвращён, и повтор — это новая попытка.

## Последствия

- Ответы моделей хранятся в Redis до суток. Это то же, что агент уже получил. Шлюз не логирует их и не отправляет
  дальше.
- Описание операции в OpenAPI не менялось, поведение описано в javadoc `SpendController` и здесь.
