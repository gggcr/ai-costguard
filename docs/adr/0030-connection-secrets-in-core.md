# 0030. Секреты подключённых систем можно хранить в ядре, зашифрованными

## Контекст
По ADR 0019 секреты подключённых систем (пароль 1С, токены Okta и банка и т.д.) живут только в окружении агента
коннекторов, ядро их не видит. Для компании без своего администратора это неудобно: подключить систему на странице
мало, нужно ещё зайти на сервер агента или в Airflow и прописать переменные. Владелец продукта решил, что пароли и
токены можно вводить прямо на странице и хранить в ядре, если они защищены.

## Решение
- **Необязательно.** `POST /api/v1/connections` принимает поле `secrets` (`{ИМЯ_ПЕРЕМЕННОЙ: значение}`). Нет поля —
  всё как в ADR 0019: секреты в окружении агента. Имена — только из `secrets` типа (`SystemTypes`), иначе
  `400 secret_unknown`; в `settings` секрет по-прежнему не пройдёт (`setting_unknown`).
- **Шифрование.** AES-256-GCM (`SecretBox`), ключ `CONNECTIONS_ENCRYPTION_KEY` (base64 32 байт, из Lockbox или
  Vault), дополнительные данные — `tenant_id:connection_id`: шифротекст, скопированный в чужую строку, не
  расшифруется. Формат: байт версии 1, 12 байт nonce, шифротекст с тегом. Без ключа секреты не принимаются
  (`503 encryption_key_missing`); временный ключ не создаётся — после перезапуска секреты было бы не прочесть.
  Колонки `connection.secrets` и `connection.secret_names` (V22).
- **Наружу не отдаются.** В `Connection` только `secretsInCore` — имена. В журнале действий — тоже имена.
  В `connectors.config.v1` (Kafka) секретов нет и не будет.
- **Агенту — по HTTPS.** `GET /api/v1/connections/agent-secrets` только для роли `connector` (сервисный аккаунт
  компании в Keycloak с `tenant_id`), отдаёт открытые секреты живых подключений по типу. Агент запрашивает их
  каждый цикл, если у него есть `CORE_URL` и `CORE_TOKEN` и `from_core` не выключен; переменная окружения агента
  главнее. Токен другой компании агент отвергает. Значения секретов ядра вырезаются из ошибок в отчётах, как и
  секреты окружения. Ядро недоступно — агент работает на секретах окружения.
- **Отключение стирает секреты**, история выгрузок остаётся. Повторное подключение приносит свои.

## Последствия
- Новые переменные: `CONNECTIONS_ENCRYPTION_KEY` (ядро), `CORE_URL` и `CORE_TOKEN` (агент; уже нужны почтовому
  коннектору). В realm Keycloak добавлена роль `connector`; клиента на каждую компанию заводит администратор.
- Потеря ключа — секреты, хранимые в ядре, придётся ввести заново; ротации ключа пока нет (в формате есть байт версии).
- Страница фронтенда работает без изменений (секреты не обязательны); поле ввода секретов описано в
  `docs/architecture/connections-page.md`.
