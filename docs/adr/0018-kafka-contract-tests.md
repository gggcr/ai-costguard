# 0018. Контрактные тесты Kafka по schemas/avro

## Контекст
Контракты Kafka лежат в `schemas/avro`. Java-классы генерируются из них, Python читает те же файлы. Проверки
раньше были частичными: часть сообщений сверялась со схемой в тестах модулей, но никто не проверял, что топик
слушается классом своей схемы. Ещё реже проверяли, что потребитель переживёт любое сообщение, которое схема
разрешает: пустые строки, null во всех необязательных полях, отрицательные суммы.

## Решение
- Java (ядро и шлюз), `TopicContractTest`:
  - каждый `@KafkaListener` перечислен в карте «топик → класс», а схема класса совпадает с файлом схемы
    топика. Слушатель без записи валит тест;
  - производители ядра проверяются в `EventMappingTest`: запись каждого события совпадает со схемой своего топика;
  - у шлюза так же проверяется `agent.operations.v1`.

  При сравнении убирается только `avro.java.string`, который добавляет генератор (`-string`).
- Python, `tests/contracts`:
  - производители (ingest, нотариус, детектор, коннекторы) строят сообщения, которые пишутся схемой своего топика;
  - потребители получают по 40–80 случайных сообщений, допустимых схемой (`samples.py`, логические типы
    соблюдаются, сообщение проходит через запись и чтение схемой, как из Kafka), и не должны падать; их ответы
    тоже проверяются схемой;
  - каждый топик, названный в коде сервиса, есть в `schemas/avro`.
- Встроено в существующие workflow:
  - java и python запускают контрактные тесты отдельным шагом;
  - contracts на изменение схемы запускает обе стороны сразу (`kafka-contracts`), даже если код сервиса не менялся.

## Последствия
- Тесты сразу нашли два «ядовитых» сообщения: ingest падал на подтверждённом файле нечитаемого типа (и читал
  его снова бесконечно), детектор — на отрицательной сумме или числе токенов. Оба исправлены.
- Новый слушатель или новый топик требует записи в карте контракта; это и есть цель.
