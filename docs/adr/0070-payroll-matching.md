# 0070. Выплата — только однозначному сотруднику; несопоставленные выплаты хранятся для разбора

Статус: предложено, 2026-11-12 (аудит безопасности, находки R1 и R1.5.1). Дополняет ADR 0054. Требует решения по
сроку хранения и по уникальности адресов: см. «Открытые вопросы».

## Контекст

Ведомость (файл) и коннектор 1С:ЗУП называют сотрудника по почте или по ФИО. Ядро брало одного из сотрудников с
совпадающим без учёта регистра адресом (`lower(email) = ? … limit 1`, работающий раньше уволенного), а при
ненайденном адресе искало по ФИО. Схема требует уникальности адреса только в точном написании, поэтому `it_admin`
может завести «двойника» с адресом в другом регистре (онбординг показывает ему пароль) и получать выплаты другого
человека, в том числе итоговую выплату уволенного; опечатка в адресе при совпавшем ФИО отдавала выплату другому.
Несопоставленные строки не хранились: для коннектора их никто не видел.

## Решение

- Адрес из строки нормализуется как в приложении (`Names.email`: пробелы по краям, нижний регистр, проверка формата)
  и сравнивается без учёта регистра со всеми нестёртыми сотрудниками компании, работающими и уволенными.
  Сохранённые адреса не обрезаются: приложение их нигде не обрезает.
- Ровно один — выплата ему (уволенному тоже: итоговый расчёт). Несколько — `ambiguous employee`, никому.
- **Если адрес передан, ФИО не используется вовсе** (R1.5.1): неверный адрес — `bad email`, ненайденный —
  `employee not found`, неоднозначный — `ambiguous employee`. Только строка без адреса сопоставляется по очищенному ФИО
  (`Names.clean`), и только с единственным таким сотрудником; тёзки — `ambiguous employee`.
- Строка без сотрудника хранится в `payroll_unmatched` (V48) как её передал источник, с причиной и числом кандидатов,
  один раз по отпечатку строки, и уходит, когда та же выплата сопоставлена при следующей загрузке. Видна только
  `owner` и `finance`: `GET /api/v1/payroll/unmatched`. Таблица под принудительным RLS, с политикой резервного
  копирования; удаляется при удалении компании и, по адресу или очищенному ФИО, при удалении данных сотрудника.
- Существующие выплаты не меняются; повторная загрузка неоднозначной строки не трогает правильно назначенную выплату.

## Последствия

- Каждый «двойник» адреса останавливает выплаты по этому адресу, пока finance не разберётся.
- Работающий и уволенный с одним адресом (в разном регистре) больше не сопоставляются автоматически.
- Тесты: `PayrollMatchingIntegrationTest`, `PayrollUnmatchedProtectionIntegrationTest`, `V48V49MigrationTest`.

## Открытые вопросы

- **Срок хранения `payroll_unmatched` не установлен** (ADR 0021 его не задаёт). Строка содержит адрес, ФИО и сумму
  выплаты, но не является учётным документом (документ — ведомость у источника). Предложение для владельца продукта и
  ответственного за персональные данные: удалять строку через 1 год после `last_seen` тем же механизмом
  `RetentionJob` с новой переменной `PRIVACY_RETAIN_PAYROLL_UNMATCHED=P1Y`. До решения автоматического удаления нет.
- **Уникальность адреса без учёта регистра** (`unique (tenant_id, lower(email)) where erased_at is null`) не
  добавлена: миграция упала бы на первых дублях в реальных данных. Сначала проверка дублей и их устранение по
  [runbook](../runbooks/security-identity.md), затем отдельная миграция.
- Интерфейса разбора несопоставленных выплат в кабинете нет, только API; закрыть строку вручную нельзя.
- Импорт техники (`EntityStaging`) при неоднозначном адресе по-прежнему пробует ФИО.
