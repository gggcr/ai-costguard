# 0040. Счётчики бюджетов в Redis восстанавливаются из журнала проводок

Статус: принято, 2026-11-10.

## Контекст

На доске счётчики бюджетов живут в Redis, а источник истины — PostgreSQL: «после сбоя счётчики восстанавливаются из
журнала проводок». В коде восстановления не было. Если Redis терял данные, лимиты возвращались из компактного
топика `budgets.limits.v1`, но `spent` начинался с нуля, и агенты могли заново потратить весь бюджет. Поле
`correction` в событии было, но ядро всегда присылало 0.

Пункт делался в два шага: сначала снимок журнала в ядре, затем его применение в шлюзе.

## Решение

**Снимок в ядре (`ledger/internal/CounterSnapshot`).** Раз в `costguard.ledger.counter-snapshot-interval`
(5 минут) каждый бюджет каждой компании снова уходит в `budgets.limits.v1`. Лимит и версия текущие: снимок лимит не
меняет. Новые поля события:
- `ledger_spent` — сколько проводки списали с бюджета до момента `ledger_as_of` (сторно вычитаются);
- `ledger_as_of` — момент на `counter-snapshot-lag` (2 минуты) раньше снимка. Операции, которые шлюз рассчитал до
  этого момента, к этому времени уже дошли до журнала.

Изменение лимита по-прежнему приходит без этих полей. Компании для обхода берутся из `ledger_tenant`: под RLS
список компаний не получить, поэтому таблицу заполняет триггер на `budget`, как `audit_tenant` у аудита. Поля в Avro
необязательные, со значением по умолчанию null, так что старые читатели их просто не видят.

**Применение в шлюзе.** `settle.lua` каждое списание пишет ещё и в журнал списаний бюджета
(`cg:{tenant}:b:<budget>:log`, сортированное множество по времени расчёта, хранится
`costguard.gateway.settlement-log` — сутки). `limit.lua` сначала применяет лимит, если версия новее, как раньше.
Если пришёл снимок, он затем выставляет `spent` = `ledger_spent` + списания из журнала после `ledger_as_of`. Отсюда
три свойства:
- счётчик, потерянный вместе с Redis, восстанавливается в пределах одного интервала;
- верный счётчик остаётся верным;
- повтор того же снимка ничего не меняет.

Если Redis потерял и журнал списаний, теряются только расчёты между `ledger_as_of` и сбоем, то есть пара минут, ещё
не дошедших до журнала проводок. Их досчитает следующий снимок, когда они там появятся.

## Последствия

- Резервы, открытые в момент потери Redis, теряются. Их расчёт вернёт «резерв неизвестен», но операция всё равно
  попадёт в журнал проводок, и следующий снимок её учтёт.
- Операция, которая началась до момента снимка, а рассчиталась после него, может посчитаться дважды: в журнале и в
  журнале списаний. Счётчик ошибается в сторону осторожности, следующий снимок это исправляет.

- Топик `budgets.limits.v1` получает сообщение по каждому бюджету раз в пять минут. Он компактный, поэтому хранится
  только последнее.
