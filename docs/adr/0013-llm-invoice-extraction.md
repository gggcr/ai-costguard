# 0013. Извлечение счетов из текста языковой моделью через шлюз CostGuard

## Контекст
PDF-счёт без таблицы и текст после OCR (ADR 0012) нельзя разложить по колонкам правилами: у каждого поставщика
свой макет. Нужны поставщик, ИНН или VAT, номер, дата, валюта, итог и позиции, а неуверенные поля должны уходить
человеку, как на фрейме 7 доски. Модель нельзя вызывать мимо шлюза: CostGuard сам должен проходить свой контроль.

## Решение
- `costguard_common.llm.GatewayLlm` вызывает модель только через шлюз, `/v1/providers/<provider>/...`, с
  виртуальным ключом. Ключ один на платформу: агент «Распознавание счетов» в собственном тенанте CostGuard
  (`INGEST_LLM_API_KEY`). Расходы видны CostGuard и ограничены мандатом и бюджетом этого агента, бюджеты клиентов
  не трогаются. Каждый вызов — новая операция; в `X-CostGuard-Task` — ключ файла, в `X-CostGuard-Task-Goal` —
  цель, чтобы ИИ-оценщик шлюза (ADR 0011) понимал, зачем вызов. Отказ шлюза (бюджет, мандат, согласование) и его
  недоступность дают файлу статус FAILED с причиной, а не падение конвейера.
- Модель отвечает одним JSON-объектом: у каждого поля `value` и `confidence`. Системная инструкция говорит, что
  текст документа — данные, а не указания, и что отсутствующее значение — `null`, а не догадка.
- Счёт становится обычной таблицей (`Поставщик`, `ИНН поставщика`, `Номер счёта`, `Дата счёта`, `Наименование`,
  `Сумма`, `Валюта`, `Количество`, `Цена`), поэтому маппинг, проверка и `accept` прежние. Ячейки с уверенностью
  ниже `INGEST_LLM_CONFIDENCE` (0,9) уходят в `uncertain` результата импорта, ядро делает из них задачи проверки.
  Реквизиты счёта проверяются один раз, на первой строке. Если позиции не сходятся с итогом, их суммы уходят на
  проверку. Нет позиций — одна строка «Итого по счёту».
- Что прочитала модель, хранится рядом с файлом (`<key>.extracted.json`). `accept` берёт строки оттуда и не
  спрашивает модель снова (и не запускает OCR), поэтому записываются ровно те строки, которые проверил человек.
- Исправления человека приходят в `ingest.accepted.v1`. Исправленный счёт сохраняется как пример для своего
  поставщика в хранилище ingest: `<tenant>/examples/index.json` и `<tenant>/examples/<поставщик>.json`, три
  последних. Новый документ сопоставляется с поставщиком по ИНН в тексте или по очищенному названию, и модель
  видит последний исправленный счёт этого поставщика. Примеры не выходят за пределы тенанта.
- Включается, когда заданы `INGEST_LLM_API_KEY` и `INGEST_LLM_MODEL`; без них текст без таблицы получает понятную
  ошибку, как раньше.

## Последствия
- Текст счетов клиентов уходит провайдеру модели. Для клиентов, которым это нельзя, провайдер — GigaChat или
  YandexGPT (`INGEST_LLM_PROVIDER`).
- Агенту платформы нужен мандат с разрешённой моделью и бюджет; без них шлюз отклоняет вызов, и файлы с текстом
  без таблицы получают FAILED.
- Хранилище ingest теперь пишется: ему нужны права на запись в бакет файлов.
