# 0069. Личность по Keycloak `sub`, а не по почте токена

Статус: предложено, 2026-11-12 (аудит безопасности, находки «подмена почты», H1, H2). Меняет ADR 0009, 0036, 0051,
0068 в части определения человека. Требует согласования команды: см. «Открытые вопросы».

## Контекст

Ядро определяло человека по claim `email` токена: кабинет сотрудника (`Whoami`, `CabinetService`), ключ подписи
(ADR 0068), владелец агента и согласования, настройки уведомлений, принятие приглашения. В Keycloak 26.0 пользователь
сам меняет почту в Account Console: функция подтверждения новой почты (`update-email`) выключена, атрибут `email`
был доступен на запись роли `user`, а при смене Keycloak только сбрасывает `email_verified`. Сотрудник со своей
учётной записью ставил себе адрес коллеги без входа и видел его зарплату и документы, подписывал за него документ и
занимал его ключ подписи. Кто согласовал операцию, тоже записывался по почте (или, в кабинете владельца агента, по
имени из токена) и попадал в хэш согласующего, который нотариус NEAR хранит навсегда (H2). Отдельно
(H1): `it_admin`, который правит карточки сотрудников и добавляет пользователей, мог через автоматическую связь
по почте при входе или через пользователя с `employeeId` получить кабинет сотрудника без входа, хотя зарплата ему
закрыта (ADR 0054).

## Решение

- **Личность — пара (realm, `sub`).** `user_account.keycloak_subject` (V47, уникальный). Человек — учётная запись с
  этим `sub` в компании токена (RLS); его сотрудник — только `user_account.employee_id`. Почта токена ничего не
  решает и только показывается, когда учётной записи нет.
- **Откуда берётся `sub`.** Приглашение, онбординг и регистрация записывают id учётной записи Keycloak, которую ядро
  само создало. V47 переносит его для существующих записей из `invitation` и `registration` (новейшее приглашение,
  не отозванное, без неоднозначностей). Остальные учётные записи связываются один раз при первом входе (`FirstLogin`,
  `LoginLinks`), только если `email_verified = true` и адрес назван ровно у одной учётной записи компании.
- **Связь с сотрудником никогда не создаётся при входе** (H1). Её дают приглашение (только `owner`), онбординг (новый
  сотрудник), `POST /api/v1/users` с `employeeId` (только `owner`, иначе 403 `employee_link_owner_only`) и разовое
  заполнение V47 по однозначно совпадающим адресам, хранящимся в базе.
- **Ключ подписи принадлежит учётной записи** (`signing_key.user_account_id`). Прежние ключи не переносятся: кто их
  создал, доказать нельзя; строки остаются, подписать ими нельзя. В подписи — имя и почта учётной записи из базы и
  `signer_account_id`.
- **Кто согласовал** (H2, V49). Решение принимает учётная запись `sub`; без неё 403 `decider_account_required`.
  `decided_by` — её сохранённая почта, `decided_by_account` — её id. Хэш согласующего v2:
  `costguard:approver:v2`, tenant_id, approval_id, id учётной записи. Хранится в `approver_hash` с
  `approver_hash_version`. Хэши v1 уже в NEAR не пересчитываются: строки помечены версией 1 и проверяются по формуле
  v1 (`NotaryHashes.approverMatches`). Контракт NEAR не меняется: он принимает любой хэш из 64 hex-символов.
- **Keycloak.** В профиле пользователя обоих realm-файлов атрибут `email` доступен на запись только `admin`. Импорт
  realm выполняется только при первом запуске, поэтому на работающих стендах это меняется вручную
  ([runbook](../runbooks/security-identity.md)).

Дополнение аудита 2026-11-13: кто сделал запись, тоже определяется по `sub`.

- Журнал действий (ADR 0022) пишет исполнителя с учётной записью CostGuard так, как компания её сохранила (имя и
  почта учётной записи, найденной по `sub`), а не как его называет токен. Раньше имя и почта токена ещё и
  перезаписывали строку исполнителя при каждом действии, то есть меняли задним числом все его прошлые записи. Вход
  без учётной записи по-прежнему записывается по данным токена; его `sub` записывается всегда.
- «Кто» в истории находки и «кто загрузил» файл импорта — почта учётной записи по `sub`. Других следов у этих
  действий нет: журнал действий о них не пишет.
- «Кто решил» в заявках кабинета (отпуска, лицензии, закупки, лимиты агентов) и имя загрузившего документ остаются
  подписью для показа из токена: исполнитель этих решений записывается в журнал действий по учётной записи.

## Последствия

- Учётная запись без `sub` не видит кабинет, не подписывает и не решает, пока её человек не войдёт с подтверждённой
  почтой. Сотрудник со входом в Keycloak, но без учётной записи CostGuard, кабинет теряет; ему нужна учётная запись.
- `it_admin` больше не связывает пользователя с сотрудником. Владелец остаётся доверенной ролью: он может связать
  любую учётную запись с любым сотрудником.
- Кто решил по согласованию v2 можно проверить, пока известен id учётной записи; после удаления данных человека id
  остаётся без учётной записи и больше никого не называет.
- Регрессионные тесты: `EmailSpoofingIntegrationTest`, `EmployeeLinkHijackIntegrationTest`,
  `ApproverIdentityIntegrationTest`, `NotaryHashesTest`, `V47LoginSubjectMigrationTest`, `V48V49MigrationTest`,
  `ActivityActorIdentityIntegrationTest`, `TokenAttributionIntegrationTest`.

## Открытые вопросы

- Согласовать ограничение прав `it_admin` (связь с сотрудником только у `owner`).
- Изменить realm на staging и prod вручную и проверить поведение на настоящем Keycloak 26.0.7 (не проверено).
- Привязка учётной записи без `sub` по подтверждённой почте опирается на то, что Keycloak сбрасывает
  `email_verified` при смене почты пользователем. Строгая альтернатива — привязка только администратором.
- «Кто решил» в заявках кабинета и имя загрузившего документ показываются из токена (имя в Keycloak человек
  меняет сам). На права не влияют, исполнитель есть в журнале действий; брать ли и их из учётной записи — решить
  команде.
