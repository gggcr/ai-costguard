# 0021. Хранение и удаление персональных данных: сроки, удаление сотрудника, удаление компании

## Контекст
CostGuard хранит данные сотрудников клиента: ФИО, почту, должность, выданную технику, лицензии и последний вход в
каждый сервис ([реестр](../privacy/data-inventory.md)). Для 152-ФЗ и GDPR нужны сроки хранения, удаление по запросу
и удаление всей компании, когда она уходит. Данные лежат в пятнадцати модулях ядра, в файлах, в ClickHouse, Kafka и
Keycloak. Часть записей — доказательства, их база запрещает менять: квитанции (ADR 0006), проводки, акты выдачи
техники. Решения о сроках по умолчанию, об актах, об удалении компании и о Keycloak приняты с владельцем продукта
2026-11-09 и ждут подтверждения юриста.

## Решение
- **Модуль `privacy`** решает, когда удалять, говорит с системами вне базы и ведёт запись. Каждый модуль с таблицами
  реализует `DataHolder`: удалить или обезличить своё о человеке (`eraseEmployee`), удалить просроченное
  (`expire`), удалить всё компании (`eraseCompany`). Модуль трогает только свои таблицы и сообщает, что сделал, в
  `Report`: счётчики, без содержимого строк. `privacy` не зависит ни от одного модуля; кто такой человек, говорит
  модуль `org` через `ErasureSubjects`. `org` выполняется последним: остальные ищут человека по почте, которую он
  стирает. Тест сверяет таблицы всех `DataHolder` со схемой: таблица без владельца не пройдёт сборку.
- **Сроки** в `costguard.privacy.retention` (ISO-периоды, переменные `PRIVACY_RETAIN_*`): уволенный сотрудник 1 год,
  активность (входы в сервисы, записи источников о людях) 1 год, уведомления 1 год, акты выдачи 5 лет после возврата
  техники, загруженные файлы 5 лет, журнал действий 3 года. Задача `RetentionJob` раз в сутки обходит компании из
  `privacy_tenant` (без RLS: под RLS список компаний не получить; заполняют триггеры), каждую в своей транзакции.
  Уволенного больше срока она удаляет тем же путём, что и запрос, с пометкой `retention`.
- **Удаление сотрудника** — `POST /api/v1/employees/{id}/erasure`, только `owner`, только уволенного (работающему
  нужны техника и доступы), не единственного владельца компании. Строка `employee` остаётся с тем же id, чтобы
  выдачи, агенты и находки, которые на неё ссылаются, не рассыпались, но больше никого не называет. Пользователи
  CostGuard этого человека удаляются: учётная запись — не история. Где запись должна и дальше говорить, что кто-то
  действовал («согласовал», «загрузил», шаг находки), почта заменяется псевдонимом `erased:<id удаления>`, одним на
  все его записи. Повторный запрос возвращает первую запись.
- **Что остаётся при удалении сотрудника, и почему.** Акт приёма-передачи — первичный учётный документ с ФИО, его
  хранят весь учётный срок (402-ФЗ, ст. 29); в записи он значится как `retained` с основанием и датой, когда его
  удалит задача. Загруженные счета и выписки — учётные документы компании, могут упоминать человека; остаются до
  своего срока. Квитанции журнала и хэши в NEAR не меняются: в них нет персональных данных (компания, операция,
  агент, сумма), а связь с человеком обезличена через запись сотрудника; хэш согласовавшего в NEAR (ADR 0009) с
  заменой почты больше не проверить. Сообщения `ingest.normalized.v1` истекают с топиком через 7 дней, логи через 30;
  запись называет обе даты. Настройку подключения, где указана почта человека, ядро не меняет само (агент перестал
  бы выгружать) и пишет в запись шаг `manual`.
- **Удаление компании** — `POST /api/v1/company/erasure` с названием компании, как оно сохранено; только `owner`.
  30 дней (`PRIVACY_COMPANY_GRACE`) запрос можно отменить (`DELETE`). Потом задача удаляет всё: каждый модуль свои
  строки, включая квитанции, проводки, акты и журнал действий; каталог файлов компании; строки ClickHouse
  (`ALTER TABLE … DELETE`, ядро идёт туда только за этим); учётные записи Keycloak с её `tenant_id`; записи
  compacted-топиков — tombstone по каждому ключу компании (`CompactedRecordsErased`, отправляет outbox). Шлюз на
  tombstone в `agents.state.v1` сразу забывает агента, его ключи перестают работать. Остаётся строка
  `company_erasure` без RLS: id компании, даты и счётчики, это и есть запись об удалении.
- **Доказательства удаляются только двумя путями.** Триггеры `receipt`, `ledger_entry`, `asset_act`,
  `activity_entry` пропускают удаление только при `app.purge = on`; его ставит `privacy` для своей транзакции (задача
  хранения и удаление компании). Изменение по-прежнему запрещено всегда.
- **Порядок: сначала системы вне базы, потом база.** Удаления в Keycloak и ClickHouse безопасно повторить. Если затем
  упадёт база, следующая попытка не найдёт там ничего и доделает остальное. В обратном порядке закоммиченное
  удаление в базе забыло бы почту, по которой ищется учётная запись. Keycloak недоступен — запрос получает
  `503 identity_provider_unavailable` и ничего не меняет.
- **Keycloak** — через Admin API от конфиденциального клиента `costguard-privacy` с правами только `view-users`,
  `query-users`, `manage-users`. Учётная запись считается компании, только если так говорит её атрибут `tenant_id`:
  одной почты мало. Секрет пуст — запись удаления содержит шаг `manual`, runbook описывает ручное удаление.
- **Outbox** удаляет доставленные события (`spring.modulith.events.completion-mode: delete`): событие — копия
  изменения, а с ним и персональных данных.

## Последствия
- Одна точка для сроков и одна запись на каждое удаление; что именно удалено в каждом хранилище, видно владельцу и
  аудитору (`GET /api/v1/erasures`). Новый модуль с таблицами обязан реализовать `DataHolder`, иначе упадёт тест.
- Удаление сотрудника занимает одну транзакцию и запросы к Keycloak; на компании с тысячами записей о человеке это
  секунды. Удаление компании идёт раз в сутки, вместе с задачей хранения.
- В Redis шлюза после удаления компании остаются счётчики бюджетов по id (числа, без людей). Ключи `agent_id:task_id`
  в `agent.risk-signals.v1` ядро не знает и tombstone им не шлёт; данных людей в них нет.
- Ядро и пайплайн хранят файлы в одном бакете (ADR 0049), поэтому удаление компании убирает и примеры исправлений
  пайплайна. Резервные копии PostgreSQL держат удалённое ещё 14 дней.
- Сроки и основание хранения актов — предмет проверки юриста ([for-lawyer.md](../privacy/for-lawyer.md)). Сменить
  срок — переменная окружения, без релиза.
